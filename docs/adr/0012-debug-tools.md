# ADR 0012: Debug tools exist only in dev and tester builds, and are controlled from outside the simulation

| | |
|---|---|
| Status | Accepted |
| Date | 13 Oct 2026 |

## Context

Testing on a headset needs to see what the solver sees (collision capsules, entity colliders), slow the simulation down and step it a frame at a time, switch each system off to find which one a problem comes from, and replay a recorded hand session. Some of this already shipped as address switches (`?debug=shadow`, `?debug=joints`, `?record`), and the judges' build contained all of it. The tools must cost nothing when off, work from a keyboard and from hands only, and never be in the judges' build.

## Decision

1. **One gate, decided at build time.** `DEBUG_TOOLS` (`src/debug/debug-flag.ts`) is `import.meta.env.DEV || import.meta.env.MODE === 'tester'`. The dev server has it; `npm run build` does not; `npm run build -- --mode tester` makes a tester build. **The mode is used, not an environment variable, because Vite turns an unset `VITE_` variable into nothing the bundler can fold**: a first version with `VITE_WSW_DEBUG` left the debug code in the normal build. The rule is that debug code is reached only through `if (DEBUG_TOOLS) { await import('../debug/...') }`, never a static import from shipped code, so the bundler removes the branch and the chunk. `scripts/check-debug-free.mjs` builds both ways in fresh processes and looks for marker strings (it must run outside Vitest, which sets `NODE_ENV=test` and so makes `DEV` true); the debug code is about 18 KB, and the normal build has none of it. The check is a script, not a unit test, because the project's tests have no Node types.
2. **Moved behind the gate:** the shadow-capsule and joint-dot views (`ShadowDebug`, `JointDots`, no longer imported by `main.ts`) and the launcher's Testing panel. The launcher's Testing panel replaces typing an address: each switch applies at once, is remembered in the browser (`wsw.testing`) and the settings panel and recording begin when VR starts, so nothing is typed or reloaded; the old address forms (`?debug=...`, `?record`) still work, quietly, for the scripts that drive the page, and only when the gate is on. **Not moved, and still in the judges' build:** the Hand Lab (`?mock=1`), `?record`, `?flicker=`, `?occlude=` and the Copy report panel; they are older, wider and not part of this task, and are listed for a decision.
3. **Slow motion and stepping wrap `FixedStepLoop.advance` from outside** (`TimeControl`): the simulation is never given a fractional step, so it stays deterministic whatever the speed. Slow motion scales the frame time (1x, 1/2x, 1/4x, 1/10x); paused advances nothing; a step request advances exactly one whole step (the loop's remainder is always under one step, so adding one step gives one). A burst of queued steps is capped at eight. `fixed-step.ts` (Teammate A's) is not changed. Only the simulation slows: hands, shadows, audio and the lantern stay in real time, so a paused game can still be poked and looked at.
4. **Systems are switched off by overrides on top of the settings** (shadow mesh hidden; sharpen strength 0; flicker amplitude 0; candle point light hidden; glove hidden), applied through one function, so changing a setting while a system is off does not turn it back on, and a switch restores what was there (the device's default flicker, say), not a guess.
5. **The controller holds no engine objects** (`DebugController`): the state, the keyboard actions and the menu's buttons live in plain TypeScript with the effects injected, so the keyboard, the on-page line and the hands-only menu cannot disagree and all of it is tested in Node.
6. **Keyboard:** Alt plus a key, on the physical key (`code`), so none clash with the Hand Lab's keys and a Mac's Alt+letter symbols do not matter. A one-line HUD shows what is not normal.
7. **Hands-only menu:** extra pages after the two settings pages in the same poke panel ([ADR 0011](0011-accessibility-settings.md)), as plain data, so the panel needs no debug code and a normal build shows none. Six buttons to a page, each with its state as its text and one line of help; a key press refreshes the text.
8. **Replay** (`HandReplay`) fills both `HandFrame`s from a recording in place of the real reader (or the Hand Lab's source), on its own clock, looping, in a headset or at a desk; the hands cue is told the hands are tracked so it does not cover the view. The demo recording is only on the dev server (`recordings/` is neither in the repository nor in a build), so a tester build on Pages cannot replay it until a recording is put somewhere it can fetch.
9. **Entity colliders** are drawn from A's `EntityStore` (a circle per live entity, 20 segments, up to 192, coloured by kind, no allocation per frame). `main.ts` has no store yet; when A adds one, `debug?.setEntityStore(store)` makes Alt+C work (tested with a stand-in store in the browser probe).
10. **Skip to a puzzle is not built.** It needs A's puzzle code and B's framework (`src/game` does not exist). It plugs in through `debug.controller.actions.register({ id, group, label, run })`: each registered action becomes a button on a page for its group, with no change to the menu.
11. **No cost when off.** With the gate off the code is not there. With it on and every tool idle, the per-frame cost is one `frame()` call that checks three flags, and `TimeControl.advance` (13.8 B a frame measured, budget 64: `time-control.alloc.test.ts`); overlays update only while shown.

## Consequences

- A tester build for the Pico is `npm run build -- --mode tester` served somewhere reachable. **The Pages workflow (not ours) deploys the normal build; deploying a tester build as well is a separate decision for whoever owns it.** Until then the dev server over a tunnel (ADR 0003) has the tools.
- The Testing launcher and the debug menu are the way to reach switches in a headset without typing an address; the keyboard works wherever there is one (the emulator, a desk).
- **Verified:** the build check; `scripts/debug-probe.mjs` in headless Chromium (every key, slow motion and stepping measured against real steps, each system off and on with the settings screen changing a value meanwhile, the overlays with a stand-in store, the demo replay driving the hands, the menu's buttons); unit tests for each module; `npm run check`. **Not verified:** any of it on a headset (that a poke presses the menu's buttons is ADR 0011's open question, and the Alt keys need a keyboard), and the cost of the overlays on a Pico.
